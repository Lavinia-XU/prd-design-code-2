## 1. 定位与边界

本规范用于将已确认的页面设计转化为可执行的Demo Coding指导、Coding Plan和逐页开发任务。它属于`prd-design-code-2`的Workflow执行规则，不维护具体页面布局、交互模式、状态表现或通用组件使用规范。

页面类型、表格、表单、搜索筛选、操作确认、状态、术语和组件规范必须从已完成“查询 → SKILL.md读取 → metadata校验”的Common Design中按需读取；存在匹配Product Design时，再按Coverage叠加其产品规则。未实际读取的Design Skill或Reference不得被描述为设计依据。

本规范负责：

- 验证设计说明中指定的已有页面、模块、组件、路由、Mock和功能链路；
- 明确页面级AI Coding指导的输出Contract；
- 约束Mock数据、Implementation Mapping Gate、Coding Plan、逐页开发和交付验证；
- 处理HTML说明书与真实代码环境之间的实现差异。

## 2. 设计与代码依据核验

### 2.1 Design Context复核

生成HTML页面级AI Coding指导前，复核当前Design Context是否已覆盖当前页面实际需要的设计能力。至少检查：

- 页面结构、内容区块、交互、状态、术语、组件规则和底部操作区布局是否已有实际读取的Common Design或Product Design Reference，或明确来自PRD、用户确认、已验证代码或AI补齐；
- 是否避免仅因已识别Common Design就默认其全部规则已被使用；每项页面设计内容均可追溯到实际知识来源；
- 若页面包含底部操作区，是否已读取对应页面类型或容器形态的Common Design页面模板结构，并继承底部操作区位置、按钮顺序和布局规则；
- 若存在Product Design，其Coverage的继承（inherit）、扩展（extend）或覆盖（override）关系是否已解析；
- 当前任务的代码可用状态（verified / partial / unavailable）是否已标记；
- 当前页面是否存在需要明确标记的AI合理补齐项；
- 真实业务事实、权限、状态流转、数量限制和业务规则是否来自PRD、用户确认或可验证代码，而非AI推断；
- 是否仍有影响页面结构、导航、规则或实现方式的待确认问题。

若页面总览确定后出现新的设计能力，必须通过Design Skill Resolver按需补充对应Reference；不得默认Step 2形成的Design Context已经覆盖详细设计阶段的全部知识。

### 2.2 当前代码环境核验

当存在Demo代码环境、用户指定代码范围、Product Design指定复用对象，或用户提到已有模块时，必须实际检查以下内容：

| 核验对象 | 核验内容 | 用途 |
| --- | --- | --- |
| 路由与菜单 | 页面入口、导航路径、Tab归属、新增位置 | 确认页面访问方式和导航实现 |
| 已有页面 | 页面结构、容器形态、区块组织、样式习惯 | 判断直接复用、框架复用或参考复用 |
| 已有组件 | 组件名称、实际路径、参数、事件和使用限制 | 确认是否可直接引用或组件复用 |
| 功能链路 | 导入导出、批量操作、确认流程、状态更新等 | 确认已有交互是否可沿用 |
| Mock与状态管理 | 字段、状态值、更新方式、筛选逻辑 | 确定Demo数据和前端逻辑实现方式 |

只有已在当前代码环境中验证存在、且满足页面需求的对象，才可在页面级AI Coding指导中写为“复用对象”。未验证对象只能写为“待核验参考”，不得假设其存在。

代码可用状态约束：

- 项目目录存在不代表代码已读取；只有实际读取并验证过的页面、组件、路由、交互和数据结构才能标记为 `verified`。
- `verified` 状态才允许写精确的真实文件路径、组件名称、Props、Events 或调用方式。
- `partial` / `unavailable` 状态下，页面级AI Coding指导只能写语义级描述和组件能力，并统一标记为“Coding 阶段待核验”，禁止凭空生成真实文件路径、组件路径、Props、Events 或调用方式。
- 代码可用状态写入 Design Context，并在 Implementation Mapping Gate 阶段复核。

### 2.3 实现方式判定

按以下顺序确定每项开发内容的实现方式：

1. 已验证的、且被用户或HTML明确指定的已有页面、模块或业务组件；
2. 当前代码环境中已验证的标准组件、成熟页面框架或功能链路；
3. 已实际读取的Product Design专属组件、Common Design页面模板推荐组件、Common Design组件映射表和组件使用规范；
4. 前述能力均无法满足时的新增实现。

组件决策必须区分两个独立优先级，分别用于“设计语义来源”和“实际复用对象”，不得混用：

- 设计语义优先级（决定设计知识来源）：Product Design 产品设计规范 > Common Design 通用设计规范 > AI 补齐。
- 具体实现优先级（决定 Coding 实际复用对象）：用户或 HTML 明确要求复用的对象 > 当前代码环境中已验证的业务组件和页面框架 > Product Design 推荐的具体实现 > Common Design 推荐组件 > 通用 iDux 组件语义推断 > 全新开发。

已验证的业务组件和页面框架优先于 Product Design / Common Design 推荐组件；不得因设计库推荐了通用组件，就跳过当前代码环境中真实可用的业务组件。

实现方式仅可使用以下分类：

| 开发方式 | 使用条件 |
| --- | --- |
| 直接引用 | 已有组件或功能链路可直接使用，仅替换数据、配置或文案 |
| 复用框架 | 已有页面的布局、结构或交互模式可复用，需要实现局部业务差异 |
| 组件复用 | 已有通用或业务组件可满足当前局部能力，需要配置参数、事件或数据 |
| 全新开发 | 不存在满足需求的已验证复用基线，且Common Design / Product Design未提供可直接复用实现 |
| 待核验 | 设计阶段未验证，需在 Implementation Mapping Gate 阶段确认真实代码对象后再定 |

已有标准组件或已有业务组件能够满足需求时，禁止重新实现同类基础能力。AI新增实现必须说明新增原因，并标记为AI补齐或新增实现，不得伪装为已有代码或Design Skill规定。

## 3. 页面级AI Coding指导

### 3.1 输出时机与依据

页面级AI Coding指导在生成HTML前完成，写入HTML对应页面说明。它必须以最新Design Context、用户已确认内容、PRD业务事实和已验证代码环境为依据。

页面级指导只描述当前页面的开发实现，不重复页面内容区块中已经明确的业务说明、交互结果或状态表现。

### 3.2 开发项编码指导表

每个页面必须按开发项输出以下表格；不得只写“使用按钮”“使用抽屉”“使用高级搜索”等泛化描述。

| 编号 | 开发对象 | 开发方式 | 复用与代码映射 | 实现要求 | 完成判定 |
| --- | --- | --- | --- | --- | --- |
| P01-C01 | 页面外壳 | 复用框架 | mapping:M01，复用已验证页面框架 | 保留标题栏、筛选区、表格、分页结构，仅替换业务字段 | 页面结构和视觉基线与参考页面一致 |
| P01-C02 | 状态组件 | 组件复用 | mapping:M02，真实组件路径由映射阶段确认 | 使用已有状态组件，沿用状态值和确认链路 | 启用、禁用、确认、失败反馈均可验证 |

表格六列分别对应开发项的结构化字段：编号（id）、开发对象（name/scope）、开发方式（mode）、复用与代码映射（mappingRef + mappingStatus + target）、实现要求（requirements）、完成判定（acceptanceCriteria）。HTML 表格是展示层，真正供 Coding 使用的必须是结构化 JSON 字段。

#### 开发项固定字段

页面级 Coding 指导中的每个开发项必须使用以下固定 JSON 字段：

- 基础身份：`id`（稳定ID，格式如 P01-C01）、`scope`（固定枚举）、`name`（开发对象名称）、`mode`（开发方式枚举）；
- 代码映射：`mappingRef`（指向 Implementation Mapping Gate 映射表条目）、`mappingStatus`（verified / pending / blocked）、`target.path`（真实代码路径）、`target.export`（导出名称）；未经过代码核验时 `path` 不得编造，可留空并标记 pending 或 blocked；
- 设计依据：`sourceRefs`（页面区块、表格字段或映射表条目引用）、`designReferences`（命中的 Design Skill 规则）、`visualBaselineRef`（视觉基线参考页面）；
- 实现要求：`requirements`（列表，把开发描述拆分为可执行要求）、`dependencies`（依赖的其他开发项或对象）、`states`（loading / empty / search-no-result / error 等）、`mockContract`（数据结构与操作后更新方式）、`prohibitedChanges`（禁止改动项）；
- 验收标准：`acceptanceCriteria`（列表）、`verificationChecks`（验证方式）。

`scope` 固定枚举：page-shell / navigation / toolbar / filter / table / form / drawer / modal / business-component / mock-data / visual-validation。

`mode` 固定枚举：reuse-framework / component-reuse / direct-reference / new-development。

#### 页面级 codingGuide 固定结构

每个页面的 codingGuide 固定为以下结构：

- `pageContext`：pageId、pageType、route、codeAvailability、visualBaselineRef，说明当前页面的实现前提；
- `implementationRules`：页面级实现规则列表（如优先复用已验证页面和业务组件）；
- `items`：开发项编码指导列表（即 pageItems）；
- `mockContract`：数据结构与操作后更新方式；
- `stateContract`：加载、空、异常、无权限等状态；
- `acceptanceCriteria`：页面级完成条件；
- `outOfScope`：防止 AI 擅自扩大开发范围。

#### 开发项拆分规则

- 每个开发项只能对应一个可独立执行和验收的实现对象，不得在一个开发项中同时混合页面框架、表格、弹窗和业务规则；
- 开发项必须具有稳定 ID，Coding Plan、Coding Execution 和 Verification 使用相同 ID 追踪，不得改名、合并或遗漏；
- 开发项必须明确依赖顺序，默认先完成页面外壳，再完成数据和 Mock，再完成核心交互，最后完成视觉回归。

涉及组件时，实现要求应尽可能明确具体组件名称、关键使用方式、参数、事件或数据结构；已验证复用对象写明实际路径、模块或页面；新增实现与已有实现的差异。如果存在多个复用对象，按主对象在前、次对象在后书写。对于已验证的产品菜单、页面或模块，可用`【对象名】`标注复用基线，例如`【资产管理】复用页面框架`。

### 3.3 总览级AI Coding指导

HTML总览页还应输出全局开发策略，并必须包含组件使用规则：

- 严格按照页面区块、表格字段、表单字段中标注的组件名称开发，不得用原生 HTML 或其他组件替代。
- 页面模板中已指定的标题栏、筛选区、表格、分页、弹窗、抽屉等组件，应按模板组件骨架实现。
- 字段表中标注为标签、链接按钮、状态徽标、下拉选择、日期范围、开关等组件的内容，必须使用对应 iDux 或公司封装组件实现。
- 未标注组件名称的普通文本/数字字段，可按常规文本渲染；如实现时发现交互含义，应回查 Common Design 组件映射表补齐。

HTML总览页至少包含：

| 输出项 | 说明 |
| --- | --- |
| 输入来源 | 说明PRD、用户确认、已解析Design Context和已验证代码范围 |
| 全局复用策略 | 说明优先复用的页面、模块、公共组件或功能链路，以及待核验项 |
| 全局Mock策略 | 说明Mock结构来源、状态覆盖范围和数据更新方式 |
| 全局编码边界 | 说明本次Demo不实现的后端、数据库、真实鉴权、外部联调等范围 |
| 组件使用规则 | 写明必须按页面区块、表格字段、表单字段和页面模板中标注的组件名称开发，不得用原生HTML或其他组件替代 |
| 视觉基线 | 属于已有业务主题或页面体系时，写明作为视觉和交互基线的真实参考页面及其映射范围 |
| 页面开发顺序 | 按父页面、子页面、弹窗或抽屉的依赖关系排序 |
| 风险点 | 说明复用对象缺失、待确认业务事实或代码环境差异 |

## 4. Mock数据与Demo实现边界

### 4.1 Mock数据要求

Mock数据用于验证Demo中的页面展示、用户操作、前端状态更新和边界场景，不得被当作真实业务数据或接口实现。

每个页面的HTML页面级AI Coding指导必须说明：

- 需要覆盖的业务对象、关键字段和状态值；
- 需要验证的空值、长文本、零值、异常值、无结果或部分成功等边界场景；
- 数据新增、编辑、删除、筛选或处置后在前端的更新方式；
- 是否复用已验证的Mock结构，以及新增字段的原因；
- 列表、表单、详情等页面容器所需的最小数据集合。

状态种类、状态流转、权限、数量限制和真实业务规则必须来自PRD、用户确认、匹配Product Design或可验证代码；不得为凑齐Mock数据而编造。

### 4.2 Demo编码边界

除非用户明确要求，Demo Coding默认不实现：

- 真实后端接口；
- 数据库操作；
- 真实鉴权或权限系统；
- 复杂算法、任务调度或异步基础设施；
- 外部系统联调；
- 当前需求范围外功能。

应使用Mock数据和前端状态模拟已确认的页面行为。若实现真实业务规则、权限、状态流转或数量限制需要不可确认的信息，必须进入待确认问题，而不是使用虚构逻辑替代。

## 5. Implementation Mapping Gate（代码实现映射阶段）

用户确认 HTML 说明书后、输出 Coding Plan 前，必须执行本阶段；无论设计阶段代码状态如何，都不得跳过。本阶段把设计说明书中的复用表达映射到当前代码环境的真实代码对象，是 Coding 前的强制门禁。

### 5.1 执行情况

- 情况 A（设计阶段 `verified`）：重新验证 HTML 中写明的页面、组件、路径、参数和复用方式；确认设计说明书与当前代码实现是否一致；补充实际复用范围和新增差异。
- 情况 B（设计阶段 `unavailable`，Coding 阶段发现代码）：读取当前代码环境；找到真实页面、组件、路由和交互；将设计说明书中的语义级组件映射到真实代码对象；必要时修正 HTML 中的 Coding 指导；不得直接绕过映射阶段开始 Coding。
- 情况 C（设计阶段 `partial`）：保留已验证的映射；对未验证对象补充代码核验；必需复用对象必须在 Gate 内完成核验，非必需参考对象可标记为“不适用”。

### 5.2 统一映射表

本阶段必须输出统一映射表：

| 设计对象 | 是否必需复用 | 设计阶段表达 | 真实代码对象 | 实现方式 | AI核验依据 | 与设计说明书的差异 | 映射结果 | 视觉参考页面 | 视觉基线范围 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |

- 设计对象：HTML 设计说明书中的页面、区块、组件或交互对象。
- 是否必需复用：由 HTML、用户确认或 Product Design 判断；满足任一条件即为必需复用对象（明确要求复用；影响页面结构、视觉基线或核心交互；Coding 指导写明“直接引用”“复用框架”或“组件复用”）。
- 设计阶段表达：设计说明书中的原始表达；语义级对象写明“Coding 阶段待核验”。
- 真实代码对象：验证后的真实页面文件、组件路径、路由或模块；未验证时留空。
- 实现方式：只能使用“直接引用 / 复用框架 / 组件复用 / 全新开发”。
- AI核验依据：记录文件路径、组件名称、调用位置、Props、Events、Slots 或参考页面结构。
- 与设计说明书的差异：实现层差异或设计层差异的具体描述。
- 映射结果：只能是 `已验证` / `全新开发` / `不适用` / `阻塞`：
  - `已验证`：AI 已找到真实代码对象，并确认路径、组件名称、关键 API 和使用方式；
  - `全新开发`：AI 已完成相关代码搜索，确认不存在满足需求的可复用对象；
  - `不适用`：该对象不是当前任务的实际实现对象，仅作为非阻塞性参考；
  - `阻塞`：设计要求复用，但 AI 无法访问代码、无法找到对象，或真实实现与设计存在无法自动解决的设计层差异。
- 视觉参考页面：需求属于已有业务主题或页面体系时，填写当前页面对应的真实参考页面文件或路由；全新页面体系填写“不适用（全新基线）”。
- 视觉基线范围：只对页面级设计对象填写，覆盖页面容器、标题层级、Tab 结构、筛选区、工具栏、表格容器、表格字段展示、状态组件、操作列、按钮位置和顺序、间距边界和空状态、高风险确认链路；组件级对象填写“继承页面基线”。
- “待核验”只允许作为 Gate 执行前的临时状态；Gate 完成后，设计说明书中的“Coding 阶段待核验”标记必须被映射结果替换并回填到 Coding Plan。

### 5.3 差异发现与处理

发现差异时，不得静默修改，也不得把复用实现直接替换为全新开发：

- 实现层差异：仅影响组件名称、文件路径或调用方式，不影响页面结构、视觉基线、交互流程和业务规则；记录到映射表和 Coding Plan 后继续。
- 设计层差异：影响页面容器、布局、表格结构、视觉层级、交互流程、状态规则或业务规则；先修正结构化设计说明和 HTML，重新获得用户确认，确认前不得进入 Coding Execution。
- 业务事实缺失：权限、状态流转、数量限制、接口约束等无法从 PRD、用户确认、Product Design 或代码中确定；进入待确认问题，不得用虚构业务逻辑替代。

### 5.4 映射完成标准

- 所有必需复用对象均已由 AI 映射到真实代码对象并标记为“已验证”，或已明确判定为“阻塞”；不得以“Coding 阶段待核验”作为 Gate 通过条件。
- 不需要复用的对象已明确标记为“全新开发”或“不适用”；非必需参考对象可标记为“不适用”，但不能影响 Coding。
- 没有未处理的设计层差异或业务事实缺失。
- 没有必需对象处于“阻塞”；必需对象为“阻塞”时不得输出 Coding Plan，不得进入 Coding Execution，AI 向用户说明阻塞原因并只请求代码环境、访问条件或设计层确认。
- 需求属于已有业务主题或页面体系时，视觉参考页面与视觉基线范围已完成映射且无未处理差异；全新页面体系标记“不适用（全新基线）”，不阻塞。
- 差异已完成分级处理；映射表纳入 Coding Plan 输入。
- 未完成映射前不得输出 Coding Plan，不得进入页面 Coding。

## 6. Coding Plan

HTML生成并经用户确认、且 Implementation Mapping Gate 完成后，才输出Coding Plan。Coding Plan以最新HTML中的页面级AI Coding指导作为直接实现基线，不在本阶段重新设计页面结构、重新选择组件或重新改变开发方式。

开始Coding Plan前，必须结合当前代码环境核对HTML中指定的已有页面、模块、业务组件和复用对象是否真实存在，以及实际路径、接口和使用方式是否一致；该核对由 Implementation Mapping Gate 完成，其统一映射表作为 Coding Plan 的复用与差异基线。

若映射阶段发现设计层差异，必须先修正结构化设计说明和 HTML 并重新获得用户确认，确认前不得输出 Coding Plan。

Coding Plan必须覆盖：

- 输入来源和已确认范围；
- 导航路径、路由、菜单、Tab或页面入口；
- 全新开发页面和参考已有页面；
- 已验证复用对象与映射结果（已验证 / 全新开发 / 不适用）；
- 新增实现功能点及其原因；
- Mock策略；
- 页面开发顺序；
- 风险点、差异和待确认项。

Coding Plan必须逐项映射HTML页面级AI Coding指导，不得遗漏、合并或自行改写开发项。只有用户明确同意后，才进入Coding Execution。

## 7. Coding Execution

按HTML左侧页面目录和页面层级拆分Coding任务，先开发父级主页面，再开发子页面、弹窗或抽屉；一个页面完成并自检后，再开始下一个页面，避免入口、状态联动和Mock数据不一致。

### 7.1 并发开发限制

- 允许并发：只读代码调研、Mock 数据整理、类型定义整理、不涉及共享页面骨架的准备工作。
- 禁止并发：共享页面外壳尚未冻结时并行开发多个页面；父页面和子页面同时 Coding；共享工具栏、表格容器、表单容器或业务组件尚未确认时并行实现；多个 Agent 分别决定同一业务组件的替代实现；Implementation Mapping Gate 尚未完成时进入页面 Coding。
- 仅当页面骨架、视觉基线、公共组件和实现映射已经冻结后，才允许并发开发完全独立的页面。

### 7.2 每页开发前确认

1. 当前页面ID、页面名称、页面类型和容器形式；
2. 当前页面的Design Context依据、AI补齐项和待确认边界；
3. HTML页面级AI Coding指导表格中的全部开发项、开发方式、复用对象和差异内容；
4. Implementation Mapping Gate 映射表中当前页面的真实代码对象、实现方式和映射结果；
5. HTML指定复用对象是否已经过代码环境验证；
6. 当前页面必须还原的区块、字段、底部操作区位置、按钮顺序、状态、边界和联动规则；
7. 当前页面的Mock数据范围与前端更新逻辑。

### 7.3 每页开发后检查

1. 页面结构、区块顺序和容器形态是否与最新HTML一致；
2. HTML页面级AI Coding指导表格中的每个开发项、开发方式、复用对象和差异内容是否落实；
3. 是否将直接引用、组件复用或复用框架擅自改为全新开发；
4. Mock数据、交互、状态、底部操作区布局和边界场景是否按已确认设计完成；
5. 是否遗漏HTML说明书中的关键字段、操作、状态或联动规则；
6. 视觉基线回归：视觉参考页面与视觉基线范围已在 Implementation Mapping Gate 中映射完成，本项为执行期回归核对；对照真实参考页面核对页面容器、标题层级、Tab结构、筛选区、工具栏、表格容器、字段展示、状态组件、操作列、按钮位置与顺序、间距边界和空状态、高风险确认链路；未完成视觉回归不得宣称该页完成。

每完成一个页面，向用户说明已完成的页面和下一开发页面；全部完成后，告知Demo已开发完毕并邀请用户提出调整。

## 8. HTML基线与差异处理

HTML设计说明书是用户确认后的页面实现基线。页面结构、页面区块、页面级开发项、指定复用对象和开发方式必须完整执行。

原始需求、用户确认、已解析Design Context和已有代码用于补充背景、查找复用对象和处理HTML未覆盖内容；不得凭个人判断静默跳过、重写或弱化HTML要求。

### 8.1 差异发现时机

出现以下情况时，先报告差异并获得确认：

- HTML指定的复用对象在代码环境中不存在；
- 已验证代码实现与HTML指定的复用对象、组件参数或开发方式不一致；
- 代码约束与用户最新确认内容、PRD明确业务事实或已解析Design Skill规则冲突；
- 实现所需的真实业务规则、权限、状态流转、数量限制或接口事实仍无法确认。

### 8.2 差异分级与处理

发现差异时，不得静默修改，也不得把复用实现直接替换为全新开发。按以下分级处理：

- 实现层差异：仅影响具体组件名称、文件路径或调用方式，不影响页面结构、视觉基线、交互流程和业务规则。处理：记录到映射表和 Coding Plan，更新 Coding Plan 后继续开发。
- 设计层差异：影响页面容器、布局、表格结构、视觉层级、交互流程、状态规则或业务规则。处理：先修正结构化设计说明和 HTML，重新获得用户确认；确认前不得进入 Coding Execution。
- 业务事实缺失：权限、状态流转、数量限制、接口约束等无法从 PRD、用户确认、Product Design 或代码中确定。处理：进入待确认问题，不得用虚构业务逻辑替代。

### 8.3 基线更新

用户反馈HTML需要调整时，先更新结构化JSON并重新生成HTML；以最新HTML作为后续Coding Plan和Coding Execution的唯一页面实现基线。若调整影响复用对象或开发方式，需重新执行 Implementation Mapping Gate。
